# 31. Command-prefix patterns — making "always allow" mean something

Status: hardened on 2026-08-27 · supersedes: — · PLAN.md item 31

## Decision (the short version)

Three of this item's four questions were answered in code before it was written down. E13.7 shipped
`generaliseCommand` and `generalisePath`: a first token, or the first two when the first is a known
driver, so `git status --porcelain` is offered as `allow bash(git status *)`; a compound command is
never generalised; a destructive first word is never generalised; and the derived rule is shown in
full before it is kept, which is what makes generalising honest at all.

The one open question was whether to replace an eighteen-entry heuristic with someone else's
139-entry arity table. The item said to measure first. **So it was measured**, by running every
command in this repository's Makefile, CI workflows and scripts — 57 of them — through
`generaliseCommand` and reading the output.

**The answer is no table, and the measurement says why: the heuristic's failure mode is not arity.**
It got the prefix length right almost everywhere. It failed on exactly one shape, and an arity table
would have failed the same way for any program not in its 139 rows.

## Spec

### 1. What shipped (E13.7), recorded

- The first token, or the first two when the first is a known driver and the second is not a flag.
- **Compound commands are never generalised.** Anything with `|`, `&&`, `;`, `>` or a subshell is
  offered verbatim.
- **Destructive first words are never generalised.** `rm`, `mv`, `chmod`, `chown`, `kill`, `pkill`,
  `truncate`, `shred`, `dd`. One approval of `rm -rf ./build` must not become a rule for every `rm`.
- **The derived rule is displayed in full** before it is stored, as the `a` option beside `y`/`N`.
- **The bare tool is never offered.** `allow bash(*)` is not a thing anyone means by approving one
  command.
- `generalisePath` does the same job for path-taking tools, widening to the containing directory.

### 2. The measurement

57 commands, from `Makefile`, `.github/workflows/` and `scripts/`. The derivation was right on 55.

| Command | Derived rule | Verdict |
| --- | --- | --- |
| `git status --porcelain` | `git status *` | right |
| `go build ./cmd/...` | `go build *` | right |
| `make check` | `make check *` | right |
| `gofmt -w .` | `gofmt *` | right — the second word is a flag, there is no subcommand to keep |
| `rm -f go.work go.work.sum` | *(verbatim)* | right — destructive |
| `printf '%s\n' '- add contract'` | `printf *` | right, and harmless |
| **`goreleaser check`** | **`goreleaser *`** | **wrong** |
| **`cosign verify-blob …`** | **`cosign *`** | **wrong** |

The two failures share one property and it is not arity. `goreleaser check` validates a
configuration file; `goreleaser release` **publishes to the internet**. `cosign verify-blob` reads;
`cosign sign` signs. A one-word rule derived from approving the safe subcommand grants the dangerous
one. The mistake is not "the prefix was too short" — it is **"the generalised rule permits a strictly
more powerful command than the one that was approved"**.

A 139-entry table fixes this for the 139 programs it lists and reproduces it exactly for the 140th.
The failure is in the *tail*, which is where a table is weakest and where its maintenance cost is
highest: 139 rows generated by somebody else's LLM, which somebody has to keep correct as programs
add subcommands.

### 3. The decisions

**No table.** `commandDrivers` stays a small list that grows by evidence, one program at a time, each
addition a decision someone made on purpose after seeing a rule they would not have chosen. This
measurement grew it by two: `goreleaser` and `cosign`. Both are now regression-tested by name, with
the reason in the test.

**Where it lives is therefore moot** — the second Decide bullet asked `//go:embed`ed JSON versus Go
source, with size-budget consequences. Twenty map entries are Go source. The question only existed
because of the table.

**The exact command as a third choice: refused.** The item leaves open whether someone who wants
exactly this command and nothing more should get a third option. They already do — that is `y`,
which runs the command once and stores nothing. A stored rule matching one exact command with its
arguments is a rule that will never match again, because the next invocation differs by a path or a
flag. Offering it would add a third key to every prompt to produce a rule with no future.

**A compound command may never be stored as an `always` rule.** The item flags this as where the
hardline blocklist and this feature meet, and says the blocklist wins. Confirmed, and for a reason
worth stating: a rule is a *prefix* match, and a compound command has no prefix that means anything —
`allow bash(make check && rm -rf /tmp/x)` is a string, not a pattern, and any attempt to make it one
requires parsing shell grammar to decide which of the two commands the user was agreeing to. They
are offered verbatim as a one-time `y` and never as `a`.

**The floor is unchanged and unreachable from here.** No derived rule, however wide, lifts a hardline
refusal. A generalisation is a decision about *convenience* within what is already permitted; it can
never widen what is permitted.

## Build leaves

- **L31.1 the driver list grew by evidence** — `goreleaser` and `cosign`, with regression tests naming
  why: approving a safe subcommand must not write a rule allowing a dangerous one. *Built.*
- Everything else in this item shipped as E13.7.
